The task

A student wants to leave a private note for their advisor. The note should be available through the intended advisor workflow but must never be sent to an AI model. Make the smallest safe change and show how you would verify it.

My answer

I added an advisor inbox at /advisor that opens the note the student already sends and lets the advisor reply, and sealed the note in code so it prints as “[private]” everywhere except that one recorded read. The boundary is the model gateway: a payload may hold only record IDs, codes and exact record text, so the note is refused in any position before a model is called. A sentinel test looks for the note in every prompt the model was handed, in model-calls.log, in every other response and in everything the server printed, and npm run mutate breaks each guard in turn to show the test fails when it should.

Try it

The advisor inbox is public, with no sign-in. Anyone can read what you send. Type nothing real.

  1. Open the planner. Type a made-up first name and tap Start.
  2. Tap “Finishing high school”, pick Northline and one Cascade certificate, and tap Continue. Answer “Not sure” to the age question, then anything for the rest.
  3. On your plan, tap “Ask an advisor now”.
  4. Under “Anything else?”, write a note with a made-up name and a 555 number, for example: “My aunt Rosa Vale can drive me to interviews. Call me at 206-555-0134.” Tap “Send to an advisor”. If the page suggests leaving the number out, tap “Send as is”, so you can see what the inbox does with it.
  5. On the next screen, follow “See what the advisor sees”. It opens the advisor inbox.
  6. Open your request in the list and press “Open the note”. That press is the one read that opens the note, and it is counted. The number shows as “[phone hidden]”, and the name as “[name hidden]” when the detector finds it. The two sample requests already hold an invented conversation, if you would rather read than type.
  7. Switch on “Show phone numbers”. The number appears, and nothing else changes.
  8. Write a short reply as the advisor and send it. Keep it invented too: the inbox is public.
  9. Go back to the planner in the same browser and follow “See your request and answer”. The advisor’s answer is there, and you can write back.
  10. Open /how, choose “What the model saw”, and search the page for a word from your note. It is not there. The same calls as raw JSON are at /api/log.

One thing can go wrong on the live site. Each server instance keeps its own queue and call table in memory. If your request or the reply is missing, or the call table is empty, a different instance answered. Reload, or send again. That gap is the first piece of missing infrastructure under criterion 1.

Acceptance criterion 1

What it asks

Capture the note and make it available through the intended advisor workflow, or explicitly identify the missing infrastructure needed to do so.

What I did

The note was already captured. The planner sent it to /api/handoff, which put it in the hand-off queue and never near the gateway. What was missing was the workflow around it. I read “the intended advisor workflow” as the full loop: the student sends, the advisor reads, the advisor replies, and the student sees the reply. The first version stopped at reading. I pushed for the rest: an inbox is useless unless they can respond. The routes behind the inbox:

  • GET /api/advisor/requests lists requests without notes. A row says a note exists without carrying it.
  • GET /api/advisor/requests/<code> opens one note and records the open: why, which request, when. Never the text.
  • POST /api/advisor/requests/<code>/status sets new, in progress or resolved, and never returns the note.
  • POST /api/advisor/requests/<code>/reply sends the advisor’s answer.
  • GET /api/handoff/<code> is what the student’s planner reads: the status and the replies, never the note or her name.
  • POST /api/handoff/<code>/reply lets her write back, so a request is a conversation.

The criterion also asks me to name the infrastructure that is missing. Two pieces are.

  • A queue that survives a restart. Today it is in memory, and on Vercel each server instance has its own, so a request can vanish on restart or land where the inbox isn’t looking. Production needs a durable queue with the note encrypted as its own field, so the store and its backups hold ciphertext.
  • Who the advisor is. The inbox is public because every student in it is invented, and both pages say so. Production puts the district’s sign-in in front of it, assigns each request to one advisor, and records the advisor’s identity with every open.

Where to see it

  • The advisor inbox, live, with two invented sample requests and anything sent from the planner.
  • src/app.js, lines 153 to 193: the advisor routes. The note is sealed where it arrives at line 132, and the list drops it at line 44.

How it is proven

AC18 reads the note back through the advisor route and requires it word for word, with exactly one recorded open. AC20 requires that the list never carries a note, and that listing, a status change and wrong turns open nothing. AC25 covers the reply: the advisor sends it and the student reads it, without her note or her name. Mutations that break the read path: “The inbox list carries the note” and “A status change sends the note back” (AC20), and “Opening a note leaves no record” (AC18). Each one makes the named check fail.

  • test/private-note.test.js, AC20
  • test/reply.test.js, AC25

Acceptance criterion 2

What it asks

The note does not enter model request payloads; enforce this at a trustworthy boundary.

What I did

Two layers, both code, neither a prompt.

  • The gateway’s closed allowlist. Every model call goes through callModel in src/core/gateway.js. A payload may hold only record IDs, decision and topic codes, and the exact text of record facts, each matching its record and key. Anything else, an extra field included, is refused before the call. I changed one thing here. The gateway used to check the object it was handed and then serialize it, so a hidden toJSON hook could pass the check and write something else into the prompt. It now copies the payload to plain data, checks the copy and sends the copy. Its errors say where the problem is, never what was there.
  • The sealed note. src/core/private.js holds the note in a private field from the moment it arrives. As JSON, a string, a template, a log line or util.inspect, it reads “[private]”. The only way to read it is Sealed.open, which needs a list to record the open in and accepts only a short closed list of reasons. The note is opened in one place, the advisor read.

A reply gets the same treatment as the note, because a reply can quote it: sealed in the queue, and never in a model payload, the log or an error.

A detector cannot be the boundary. I ran Rampart Edge, a personal-details detector, over 40 invented notes. It found every email and street address and 6 of 7 names. It passed all 12 of the most private notes, a parent’s job loss, an eviction, a health worry, because they hold no identifier. A detector finds contact details. It does not know what is private. So it helps a person instead: it suggests the student leave contact details out, and it hides details in the inbox until the advisor switches each kind on.

The server never runs any model on a note, not even the detector. Rampart Edge runs only in the student’s browser and the advisor’s browser, the two places that already hold the note in the clear. It is served from this site, with no request to any other host.

Where to see it

  • /how, “What the model saw”: every call this server instance made, word for word.
  • src/core/gateway.js, lines 182 to 186: the copy is checked before anything leaves. The allowlist is lines 49 to 78.
  • src/core/private.js, lines 9 to 37: the sealed note.
  • public/rampart.js, line 5: the detector loads from this site’s own folder.
  • /report: the detector’s results on all 40 notes.

How it is proven

AC19 puts the note into 212 placements across both payload shapes: in place of each string, after each string, and as a new field on each object, as plain text, as a sealed value and inside an object. Five of the 212 are objects that try to show the check one thing and the prompt another. The gateway refuses every one before the model is called, and no rejection message holds the note. AC22 fails if any page, script or style names another host, and runs the real detector inside npm test with a check that it asked no other host for anything.

Mutations that break it: “The gateway checks the object it was handed, not the copy it sends”, “Extra fields are allowed in a model payload” and “A refused payload is quoted in the error” (AC19), and “The detector is loaded from a CDN again” (AC22).

  • test/private-note.test.js, AC19
  • test/rampart.test.js, AC22

Acceptance criterion 3

What it asks

Add an automated regression test (for example, a sentinel and model-calls.log inspection) that would fail on leakage.

What I did

AC18 plants the string SENTINEL-7Q4-PRIVATE in a note, with a 555 number and a sentence about a parent’s job. It sends the note through the browser’s own request builder, keeps the app busy with more plans and questions after the note is in the queue, and pushes the note at the two endpoints that do reach the model. Then it looks for the sentinel, the number and “lost his job” in:

  • every prompt the model was handed, recorded by a spy at model.complete, and that the spy and the gateway count the same number of calls;
  • every line of model-calls.log;
  • every response that is not the advisor read: the inbox list, the public log, the records, the hand-off reply, and the replies to each request that pushed the note at the model, to an unknown request and to a body that isn’t JSON;
  • everything the server printed, through console and raw writes to stdout and stderr;
  • the queue itself as JSON, as a string, in a template, through util.inspect and as a structured clone.

It looks past model-calls.log because the gateway writes that log. A change that calls the model around the gateway never appears in it, and a check that reads only the log passes. One mutation does exactly that: it adds model.complete(raw) to the hand-off. The log stays clean. The spy at the model sees the note, and AC18 fails.

npm run mutate copies the repo to a scratch folder, breaks one guard, runs the tests and requires the named check to fail. It does this for every guard in the list, and /report shows the last full run, guard by guard.

Where to see it

  • test/private-note.test.js, lines 41 to 136: AC18. The spy is at line 19.
  • scripts/mutate.mjs, line 63: the call around the gateway.
  • model-calls.log from the last test run.

How it is proven

Run it yourself. Node 20 or newer, no install, no keys.

git clone https://github.com/mrcoven94/pathways-next-step/
cd pathways-next-step
npm test
npm run mutate
npm start

npm test runs every check and ends with PASS or FAIL. npm run mutate breaks each guard in a scratch copy and prints CAUGHT or SURVIVED for each. npm start runs the app and prints the address to open.

Mutations aimed at AC18, beyond the call around the gateway: the note kept in the queue as plain text, a sealed note that gives up its text as JSON, the note printed to the server log, and the parser’s error sent back for a body that isn’t JSON.

Acceptance criterion 4

What it asks

Explain what the test proves, what it misses, and how the behavior would differ in production.

What it proves

  • The note reaches the advisor word for word through the advisor read, and one read is exactly one recorded open.
  • It appears in no prompt handed to the model, no line of model-calls.log, no other response, nothing the server printed and no copy of the queue, including calls made after the note is in the queue.
  • The gateway refuses it in 212 placements across both payload shapes, before any call.
  • Breaking any one guard makes its named check fail, including a call to the model that the log never sees.

What it misses

  • The browser. The inbox shows a student’s text to an advisor. The page escapes it and a content security policy blocks outside code, and I checked a script-tag note by hand, but no automated test drives a real browser.
  • A model client the test doesn’t inject. The spy sees calls through the app’s model. Code that built its own client and called a provider would not be seen. The guard for that is review, plus a lint rule in production that only gateway.js may import a model client.
  • The host. Vercel’s request logs, a crash dump or an error tracker could hold a request body. Nothing in the repo can test that.
  • The raw request. For one function call, before sealing, the note is a plain string in the request body. A debugger or a heap dump would show it.
  • An advisor who copies it. Once a person reads the note, software can’t stop them pasting it into a chat tool.

How production differs

  • Storage. A durable queue with the note encrypted as its own field, so the store and its backups hold ciphertext.
  • Who the advisor is. The district’s sign-in in front of the inbox, each request assigned to an advisor, and the advisor’s identity recorded with every open.
  • Retention. Hand-offs are deleted 90 days after they’re resolved.
  • The model. A real provider goes behind the same gateway, under zero retention, with egress from the server limited to that provider. A daily canary student leaves a sentinel note and searches the provider-side log for it.
  • Logging. Request bodies are never logged at the host, and the error tracker is set to drop them.

What review changed

Claude (Fable 5.2) orchestrated, and Opus 5.5 agents built each change. Sol 6.1, a different model run through Codex with read-only access, reviewed the plan before any code and each diff after. The one exception is the last change to the inbox, which only removed code and was not sent back. I decided what to fix and what to reject. Every correction is logged in docs/process.md, entries 14 to 18.

  • Pull request 8, the sealed note and the inbox: 10 findings, 5 on the plan and 5 on the diff. Nine were fixed. The tenth, the in-memory queue, is named under criterion 1.
  • Pull request 9, the detector served from this site: 4 findings, all fixed.
  • Pull request 10, the open inbox: 6 findings on the per-browser key version, all fixed before the key came out.
  • Pull request 11, the report: 6 findings, all fixed.

Three findings taught me the most.

  • A payload with a hidden toJSON hook passed the gateway check and put the sentinel in the prompt. Sol reproduced it while reviewing the plan, before I had changed any code. That is why the gateway checks the copy it sends.
  • The gateway refused the note in every position, then quoted it in the error: task: "<the note>" is not an allowed task. AC19 only checked that an error was thrown. Rejections now say where, never what, and AC19 reads every one.
  • With the real detector, “My ID number is 1234567890” came back as an ID inside a phone number. The merge kept only the phone, so switching phone numbers on showed the ID. A merged span now remembers every kind in it and shows only when all are on.

The mutation run caught weak checks I wrote, twice. On Nov 3, breaking the app’s default time zone survived, because AC5b passed the time zone in by hand and never tested the default. On Nov 10, sending the parser’s error back for a body that isn’t JSON survived, because the parser quotes only the first ten characters and AC18 looked for the whole sentinel. A partial echo of a note is still a leak, so AC18 now requires the fixed sentence word for word. I also wrote a getter check that expected the wrong result, and twice changed code before its check, against the order the repo asks for.

Three times I overruled the AI.

  • The first inbox sat behind a shared access code. I said: “Remember no passwords.” Claude then built a random key per browser. I said a demo with invented students needs an honest label, not a mechanism. The inbox is public, and the planner and the inbox both say so.
  • After Sol flagged loading the detector from a CDN, Claude dropped the detector from the inbox. That fixed the third-party problem by removing the feature. I said to incorporate Rampart and serve it from our own site. It is now vendored, with a manifest of sizes and SHA-256 hashes that AC22 checks.
  • The first inbox let an advisor read a note and nothing more. I said an inbox is useless unless they can respond. The advisor can now reply, and the student sees the reply in her planner.

What I would do next

  • District sign-in in front of the inbox, and a durable queue with the note encrypted as its own field.
  • Say who opened a note. The inbox shows how many times a note has been opened and when. It cannot say by whom until there is a sign-in.
  • Arjun’s point: a troubling sentence can use no trigger words. The crisis check is a fixed pattern list. After the call I ran the two phrases he raised through it. “I want to disappear” and “my parents kicked me out and I have nowhere to sleep” both fall through: each is treated as a question the records can’t answer and offered an advisor, with no 988 and 911 card. I had told you a help card covered it. It does not. I wrote a patch the same day and did not ship it. Review found ten likely phrasings it still missed and three ordinary questions it wrongly caught, and a student with nowhere to sleep should reach an advisor, not a self-harm card that blocks the request. That needs its own route, and it is ticketed. A list will always have a gap. The next layer is a small model that only classifies and never replies, running on our own infrastructure so no student text goes to an outside provider. It has to respect the rule under criterion 2, so it starts with the question box, which is not private text for an advisor, or it runs in the browser, as the detector does.
  • Why the inbox is simply open. A demo with invented students needs an honest label, not a mechanism. For a public demo that might get real text typed into it, a good halfway step is a random key per browser, so each visitor reads only what their own browser sent, with nothing to type. I built it, had it reviewed, and took it out as more than this demo needs. Sol found no way for one browser to read another’s note, and six gaps around that, all fixed before it came out.
